# Developing GigglyBits

How this extension is built, run, tested and shipped. Most of it follows practice already settled in the sibling extensions under `d:/Inetpub/vscode_extensions` (copirate, markdown-compass, json-dump, xml-dump, markdown-cfml-syntax). Where gigglybits departs from them, this file says so and why.

## Quick start

```bash
npm install
npm test          # type-check the tests, then run Jest
```

Then press **F5**. A second VS Code window opens (the Extension Development Host) running this working tree, with your installed extensions and themes still loaded. Run **GigglyBits: Open Theme Lab** there.

## Two ways to run it, and which one you are looking at

| | F5 (Extension Development Host) | Installed build |
|---|---|---|
| Runs | The working tree, rebuilt on save by the `watch` task | The last `.vsix` you installed |
| Picks up an edit | Reload the dev host window (Ctrl+R in it) | Only after `Build: Quick Development` **and** a window reload |
| Use it for | Day-to-day iteration and debugging with breakpoints | Living with the theme in your everyday window |

The trap is assuming your everyday window runs your latest source. It runs the installed `.vsix`, so a fix that works under F5 does nothing there until you package, install and reload. (Copirate records the same gotcha for its own development.)

A window reload restarts the extension host. If an AI agent is driving a session in that window, the reload ends the session, so reload by hand rather than asking the agent to do it.

## npm scripts

| Script | What it does |
|---|---|
| `check-types` | `tsc --noEmit` over `src/` |
| `check-types:test` | The same over `src/` and `test/` (`tsconfig.test.json`) |
| `lint` | ESLint over `src/` and `test/` |
| `compile` | `check-types`, `lint`, then a development bundle to `dist/` |
| `watch:esbuild`, `watch:tsc` | Rebuild and type-check on save (the `watch` task runs both) |
| `package` | All checks including test types, `themes:check`, a minified production bundle, then `smoke:bundle` |
| `smoke:bundle` | Load `dist/extension.js` with a stub `vscode` module, call `activate()`, and fail unless every contributed command is registered, every webview asset is present and every `contributes.themes` file exists and parses |
| `themes` | Generate the Lab theme and the 12 slot themes from the base palette in `scripts/build-themes.js` (see [Building the theme itself](#building-the-theme-itself)) |
| `themes:check` | Fail when those 13 theme files or `contributes.themes` are out of date; writes nothing |
| `test` | Type-check the tests, then run Jest |
| `verify` | `check-types`, `lint`, `test`: run this before you commit |
| `clean` | Delete `dist/` and `out/` |
| `pack` | `vsce package`, which runs `package` first through `vscode:prepublish` |
| `build:pack` | `clean`, then `pack` |
| `install:local` | Install the `.vsix` for the current version into your everyday VS Code and confirm it is listed |
| `dev:quick` | `build:pack`, then `install:local` |
| `version:patch` | Bump the patch version without a git tag |
| `full:patch` | `version:patch`, then `dev:quick` |

`install:local` uses `code.cmd` on Windows. Set `VSCODE_CLI=code-insiders` to target Insiders.

## Build layout

- **esbuild bundles `src/extension.ts` into `dist/extension.js`**, the same shape as `markdown-compass/esbuild.js` and copirate. The small siblings compile with plain `tsc` to `out/`. Gigglybits bundles because it has a runtime dependency (`jsonc-parser`): bundling folds it into one file, so the package ships no `node_modules`.
- That is why `jsonc-parser` sits in `devDependencies` and `pack` passes `--no-dependencies`. Any new runtime library goes in `devDependencies` too; esbuild bundles it.
- esbuild only strips types. Type errors come from `check-types`, which every build path runs first.
- **`mainFields: ['module', 'main']` in `esbuild.js` is load-bearing.** Without it esbuild picks `jsonc-parser`'s UMD build, which loads its own files through a `require` esbuild cannot follow. The bundle then builds cleanly and fails at activation with `Cannot find module './impl/format'`, so the command shows in the palette but reports "command not found". Type checks, unit tests and a grep for `require("...")` all miss it, because the tests run on `src/` and minification renames `require`. `smoke:bundle` catches it, and `package` runs it on every build.
- When the installed extension misbehaves, the extension host log has the real error. Search `%APPDATA%/Code/logs/<newest>/window*/exthost/exthost.log` for the extension ID.
- `media/` (the webview scripts and styles) is shipped as-is, not bundled. `src/identity.ts` requires `../media/shared.js`, and `scripts/theme-builder.js` re-exports `media/themeBuilder.js`, which requires `./shared.js`; esbuild bundles those copies into the extension host.
- **The retired per-folder color** is `src/identity.ts` (the old overlay's shape, `drawnOldColor`, the old color VS Code still draws, which the Frame row's note names, `oldFolderColor`, which adds a pinned color for the offer, `withoutIdentity`, which removes it, and `shouldOfferMigration`; no `vscode` import, covered by `test/identity.test.ts`) and `src/identityController.ts`, which registers no command and writes no overlay. At activation, in a folder that still has an old color and has not been offered before, it sets `workspaceState` `gigglybits.frame.migrationOffered` and offers a project theme: **Make project theme** runs `gigglybits.openThemeLab` with `{ frame: { color, style: 'filled' }, name }`, **Remove the color** writes `withoutIdentity` and clears `gigglybits.identity.hue` and `pinnedColor` at the Workspace target when they are set (both are undeclared since 0.1.1, so a write VS Code refuses is ignored and the inert value stays), and **Not now** does nothing. `onStartupFinished` activates the extension so the offer can run when a folder opens.
- `esbuild.js` copies `codicon.css` and `codicon.ttf` from `@vscode/codicons` into `dist/codicons/` on every build, because `node_modules` is not packaged. `smoke:bundle` fails if they, or any `media/` file a webview loads, are missing.

## Release loop

This is copirate's `/copirate-bbi` loop scaled down. That prompt only deploys in the copirate workspace, so here it runs as tasks and scripts.

1. Bump: `npm run version:patch`, or `npm version minor --no-git-tag-version` for a feature drop.
2. Add a `## x.y.z` entry to `CHANGELOG.md` for user-visible changes. One short bullet per change, written for someone using the extension. Internal refactors, test changes and tooling get no entry. This is the json-dump format.
3. `npm run dev:quick` (or the `Build: Quick Development` task).
4. Reload your everyday window by hand.
5. Keep the last three `.vsix` files and delete older ones:

   ```powershell
   Get-ChildItem *.vsix | Sort-Object LastWriteTime -Descending | Select-Object -Skip 3 | Remove-Item
   ```

`full:patch` does steps 1 and 3 in one go, but skips the changelog. Use it only for builds with nothing user-visible to record.

## Webview rules

There are two webview panels, each with its own view type; the Theme Lab has the command, and the Theme Preview opens with it in a window of its own:

| Panel | Host | Page script | Holds |
|---|---|---|---|
| Theme Lab (`gigglybits.themeLab`) | `src/themeLabPanel.ts` | `media/themeLab.js` | The Palette Lab: steps 1 Pick your colors (with the installed-theme list and saved themes), 2 Check readability, 3 Frame and accent, 4 Color by purpose, 5 Fine-tune a part (the Edit dock), 6 Try it, then save, and the Preview card (whether the Theme Preview window is open, and Open Preview). The page draws no preview of its own |
| Theme Preview (`gigglybits.themePreview`) | `src/themePreviewPanel.ts` | `media/themePreview.js` | The Workbench drawing and every widget family in the candidate's colors (`GBPalette.renderPreview`); a clicked part goes back to the Lab |

The Palette Inspector, a debugging view of the active theme, was removed before 0.1.0; the Theme Lab and its preview cover what users need. Both panels follow the pattern copirate uses across its webview providers (`copirate/src/providers/ChangeWalkerWebviewProvider.ts` is a clean example):

- **Content Security Policy** as a meta tag: `default-src 'none'; style-src ${webview.cspSource}; script-src 'nonce-${nonce}'`, with a fresh random nonce on every render.
- **Load files through `webview.asWebviewUri`**, and set `localResourceRoots` to `media/` and `dist/codicons/`.
- **No inline `style` attributes and no `<style>` blocks**, because the CSP blocks both. Set styles from script through the DOM (`el.style.color = ...`), which the CSP allows, or put them in a stylesheet. Both panels load `media/base.css` for the base text, button, badge, tab and toast styles, then `media/gallery.css`, `media/themeLab.css` and `media/palette.css` (`labPageHtml` in `src/themePreviewPanel.ts`).
- **Space with the shared tokens and build tabs with `GB.tabs`.** `media/base.css` opens with `--gb-space-1` to `--gb-space-6` (4, 8, 12, 16, 24 and 32px), `--gb-radius`, `--gb-border`, `--gb-text-sm` and `--gb-heading-size`, `themeLab.css` uses them for every nonzero gap, padding and margin, and new rules in the other stylesheets should too; older `palette.css` and `gallery.css` rules still use px. `GB.tabs` in `media/shared.js` builds a tab set by the ARIA tabs pattern: roving tabindex, arrow keys that wrap, Home and End, and inactive panels kept in the page with `hidden` so their inputs hold their values. The Theme Lab layout is the council's contract, `.copirate/working/prototypes/theme-lab-council/CONTRACT-v4.md`. Above the grid, `.gb-lab-top` (2rem) holds Expand all / Collapse all. Since 2026-11-07, by the user's decision, the Lab is one column at every width (it was two panes from 75rem): `.gb-tasks` holds the Preview card, steps 1 to 5 and the step 6 bar, every step at full width, with the bar sticky at the bottom and the dock's key list capped and scrolling inside it. A `ResizeObserver` on the bar publishes `--bar-h` for the focus scroll margin. `fitToWidth` zooms the Workbench drawing to the frame's width, never above 1, zooms it down further when it is taller than its row, and stretches the window's middle row to fill the height left. The design rules behind these choices are in the `webview-ui-design` Copirate topic.
- **Give every disabled control its own style.** `media/base.css` styles every button alike and has no disabled rule, so a disabled button looks and hovers like an enabled one unless the panel's stylesheet dims it, as `.gb-pl-buttons button[disabled]` in `palette.css` does. A jsdom test can only read the `disabled` property, so check a new disabled state live as well: 0.0.9's blocked save passed its unit test while looking clickable.
- **Build DOM with `textContent`, never `innerHTML`.** Theme files and settings are user-controlled text.
- **Color everything with `--vscode-*` CSS variables.** A webview that hard-codes colors breaks the moment the theme changes, which here is the whole point. The one exception is a Palette Lab candidate: its colors are the subject being judged, so `palette.js` sets them as literal hex values.
- **Messages are a typed union** on each side (`FromWebview` in each panel). Add a case there and in that panel's page script together.
  - Theme Lab: the page posts `ready` and `copy`; the Palette Lab posts through `ctx.post`, which `themeLab.js` passes on to `vscode.postMessage`, so `applyPalette`, `saveTheme`, `useTheme`, `deleteTheme`, `saveGroup`, `setGroupOn`, `deleteGroup`, `changeDefaultTheme` and `removeLeftovers` need a case in `ThemeLabPanel` only. The host sends `library`, `start`, `themeScope`, `leftovers`, `identity`, `modernUI`, `previewDetached`, `installedStarters`, `frameSeed` and `pickPart`. The Start step's tabs are Wheel and Saved; a ui state whose `startTab` is anything else, such as a `paste` or `shipped` saved before those tabs were removed, opens on Wheel (`stateOf` in `media/palette.js`).
  - Theme Lab start-up: on `ready` the host posts, in order, `modernUI`, `previewDetached`, `library`, `start`, `themeScope`, `leftovers`, a pending `frameSeed` when there is one, `identity` (with `changed: false`), and `installedStarters`. `start` carries `startConfig()` from `src/labStart.ts`, decided from the active theme's label (`captureThemeSnapshot().label`): `{ lastTry }` (under GigglyBits Dark (Lab), the record Try stored), `{ saved }` (under a bound slot), `{ note }` (why the Lab starts from the defaults, only under the Lab theme with no Try record or an empty slot) or `{}` (any other theme, which is a new user's first open, or no active theme known). `identity` carries `{ fill, regions }` from `IdentityController.current()`, or `null` with no folder or no identity, and is posted again whenever a `gigglybits.identity` setting changes (`changed: true`, including the controller's own writes) or the color theme changes (`changed: false`). `themeLab.js` applies them only on a fresh open, meaning `vscode.getState()` returned nothing: the first `start` calls `GBPalette.restoreTry` and picks the Wheel tab, for a Try of pasted colors too, or `GBPalette.loadSaved` and picks the Saved tab, and the first `changed: false` identity sets the palette's identity regions. After that, and on a revived tab, only `changed: true` touches the regions; every identity message updates the preview fill (`ctx.identityFill`, never saved to state). A note renders as `ctx.startNote` at the top of Start from.
  - Try in VS Code's `applyPalette` message also carries `settings` (mode, rule, hue, lightness, chroma, pasted colors, the editor accent index, surfaces, the frame `{ index | color, style }`, and color edits when there are any). `parseTryRecord` still keeps a `baseId` and `baseName` an older Try recorded, from when a Lab could start from a shipped theme, and `restoreTry` drops them from the ui state. After the theme settings are written, and before the information message (which resolves only when dismissed), `ThemeLabPanel` stores `parseTryRecord(settings)` in the extension's `globalState` under `gigglybits.themeLab.lastTry`; a record that fails the check is skipped and the Try goes ahead.
  - Theme Preview window: the Theme Lab page posts `previewState { palette, syntaxSets }` (its Palette Lab state and the library's syntax sets) after every `saveState` and every Palette Lab redraw, and `openPreviewWindow` from the Preview card's **Open Preview**. The window is the Lab's only preview. `ThemeLabPanel` keeps the latest `previewState`, passes each one to the open `ThemePreviewPanel` (`src/themePreviewPanel.ts`, view type `gigglybits.themePreview`), and opens that panel on `openPreviewWindow`, or reveals it when it is open. A Lab opened with `ThemeLabPanel.show` (not a revived one) also opens it on its first `ready`, before posting `previewDetached`, so the preview opens with the Lab; a later `ready` never reopens a window the user closed. On open it runs `workbench.action.moveEditorToNewWindow`, then `workbench.action.enableCompactAuxiliaryWindow`, in that order, because the second acts on the focused window. It does not run `workbench.action.enableWindowAlwaysOnTop`: the window is an ordinary one that VS Code can come in front of. The Theme Preview page (`media/themePreview.js`) posts `ready`, receives `state { palette, syntaxSets }` (the last state again on `ready`) and draws it with `GBPalette.renderPreview` as one scrolling page, a Workbench section then a Widgets section of the families in `widgets`, keeping its scroll position across redraws, and posts `pickPart { part }` for a clicked part, `part` being `describePart`'s plain values. The host reveals the Lab panel with `preserveFocus` false, so the Lab tab takes focus, then forwards it to the Lab page as `pickPart`, where `GBPalette.setPicked` opens it in the Edit dock. The dock's contrast info for the pick comes from drawing the picked card off the page (`pickedInfo`). After a reload or a restart the preview comes back with the Theme Lab. VS Code saves the window layout before `deactivate()` runs, so closing the panel there never helped: without a serializer VS Code reopened the preview's window empty. `src/extension.ts` now registers a serializer for `gigglybits.themePreview` (with the `onWebviewPanel:gigglybits.themePreview` activation event), and `deactivate()` leaves the panel alone. The serializer calls `ThemePreviewPanel.revive(panel, extensionUri, keep, state, onPick, onClose)`; `keep` is true when a Lab is open (`ThemeLabPanel.isOpen()`) or a Lab tab is in `vscode.window.tabGroups` (`hasWebviewTab`, matching the end of the webview view type, since VS Code adds a `mainThreadWebview-` prefix). Kept, the panel is the live preview again, in its own window at its old size, drawn from `ThemeLabPanel.latestPreviewState()` or the Lab's next `previewState`; otherwise, or when a preview is already open, it is disposed and its window closes. Picks and the closed notice go through `ThemeLabPanel.pickFromPreview` and `ThemeLabPanel.previewClosed`, which reach whichever Lab is open. The Roles step posts `previewHighlight { keys }` for the open role (an empty list when none), sent only when the list changes (`highlightRole` in `media/palette.js`); pointing at or focusing a row posts nothing, because scrolling the preview on every hover made it jump. A role's **Show where** posts `showWhere { keys }`: the host opens the Theme Preview, or brings it forward, then highlights those keys with `scroll`. `ThemePreviewPanel.highlight(keys, scroll)` forwards each list as `highlight { keys, scroll }` and keeps both, sending them again when the page posts `ready`; the page scrolls to the first outlined part only when `scroll` is true, so a window that is still loading still outlines them; the page gives every drawn part whose `data-keys` names one of them the class `gb-pl-role-hl`, kept across redraws and not saved. The Roles step groups a role's keys by part of the window with `KEY_AREAS` (first prefix match wins, else Text and general) and words each key with `plainKey`, made from the setting name. Both panels build their page with `labPageHtml`, one CSP and stylesheet list.
  - Detached preview: `ThemeLabPanel` posts `previewDetached { detached }` on `ready`, after `openPreviewWindow`, and from the `onClose` callback `ThemePreviewPanel.open` takes, which runs whenever the window's panel is disposed; `detached` is `ThemePreviewPanel.isOpen()`. `themeLab.js` passes it to `GBPalette.render` as `ctx.detached` without saving it, and the Preview card's line says whether the window is open. The page has no preview band: one column of the Preview card, steps 1 to 5 and the bar.
  - Modern UI: both panels (`ThemeLabPanel`, `ThemePreviewPanel`) post `modernUI { modernUI: { modern, uppercase, tabStyle, activityBar } }` when their page posts `ready`, and again on a configuration change where `affectsModernUI(event)` is true. `src/modernUI.ts` holds `modernUISettings()`, which reads `workbench.experimental.modernUI` (default true), `workbench.experimental.modernUIUppercaseViewHeaders` (default false), `workbench.experimental.modernUIEditorTabStyle` (`'pill'`, otherwise `'connected'`) and `workbench.activityBar.location` (`'top'`, `'bottom'` and `'hidden'` as given, otherwise `'default'`), the list of those ids as `MODERN_UI_SETTINGS`, and `affectsModernUI`. Each page keeps the latest value without saving it to state and redraws: `themeLab.js` passes it as `ctx.modernUI` to `GBPalette.render`, `themePreview.js` to `GBPalette.renderPreview`, and `palette.js` puts it in every gallery context it builds. `gallery.js` draws the Workbench card from `context.modernUI`: absent, or `modern: false`, is the classic drawing; `modern: true` adds `wb-modern` (and `wb-pill` for the pill style) to `.wb`, paints the shell with `modernUI.shellBackground`, the side bar, chat view and editor area borders with `surface.border`, the panel's with `modernPanel.border`, and the active editor tab, activity item and panel tab with the `modernEditorTab.*`, `modernActivityBarItem.*` and `modernTab.*` keys in place of the classic ones. `activityBar` places the activity bar independently of `modern`: `'default'` draws the classic `.wb-activity` column; `'top'` and `'bottom'` draw no column (`.wb` gets `wb-noact`) and put a `.wb-actrow` of icons, painted with the `activityBarTop.*` keys and bordered with `sideBarActivityBarTop.border`, in place of the side bar title or after its `.wb-tree`; `'hidden'` draws neither. Labels are written in mixed case, and every drawn preview's root gets `gb-upper`, which `gallery.css` turns into capitals, under the classic UI or with the uppercase setting on.
  - Modern UI colors: GigglyBits themes set none of the modern keys, so `GB.modernUIDefaults(colors)` (`media/shared.js`) works out each one the colors leave unset from VS Code's dark default rules: `modernUI.shellBackground` = `titleBar.activeBackground`; `surface.background` = `sideBar.background`; `surface.border` = `foreground` at alpha 0.15 made opaque over `surface.background`, each channel `bg - a * (bg - fg)` truncated as VS Code's RGBA does; `modernPanel.border` = `surface.border`; `modernTab.activeBackground` = `list.inactiveSelectionBackground`; `modernTab.activeForeground` = `list.inactiveSelectionForeground`, else `foreground`; `modernEditorTab.active*` and `modernActivityBarItem.active*` = the matching `modernTab.active*`. A key the colors already hold is left out, as is one whose source is missing. The Palette Lab draws with the candidate's colors plus these (`galleryContext` and `scoped`), while the Edit dock reads the candidate's colors alone and shows a modern key the candidate leaves unset with its worked-out value and a note that VS Code works it out.
- **State**: the panels are created without `retainContextWhenHidden`, so a hidden tab is torn down and rebuilt. The Palette Lab's ui state, including the chosen Start from tab (`startTab`) and the step 1 source line (`sourceLabel`), survive through `vscode.setState`, and each host re-sends its data when the page posts `ready`: the Theme Lab the library, the Theme Preview the last state. A state saved before the preview moved to its window drops `previewTab` and `previewPinned`, and one saved while the Lab chose widget families drops `widgets`; the preview window draws every family in the gallery's catalog order (media/gallery.js `CATALOG`). Which of steps 1 to 5 are open is saved too, as `sections` (step numbers; a fresh state is `[1]`, Start alone). Each step heading is a `gb-step-btn` that toggles its own entry, a pick (`openDockOn`) adds 5 and touches no other step, and step 6 never collapses. The pick, the Edit dock, the Roles step's open families and role editor, and the step 6 result line live in `palette.js` and are never saved: a reload opens with the dock closed. Copirate turns `retainContextWhenHidden` on in many places but has no recorded policy, so this repo keeps the cheaper default until a reason appears.
- **Scripts load in order**, each with the nonce. `shared.js` (DOM builder and color math, as `window.GB`) comes first in both, because the scripts after it read `window.GB` when they load. Theme Lab: `shared.js`, `themeBuilder.js` (the theme builder, as `window.GBBuilder`), `gallery.js` (the element gallery, as `window.GBGallery`, whose drawings the previews reuse), `colorPicker.js` (the color picker, as `window.GBColorPicker`), `palette.js` (the Palette Lab, as `window.GBPalette`), then `themeLab.js`. The Theme Preview page does not load `colorPicker.js`; `palette.js` reads `window.GBColorPicker` only when it makes a picker, which only the Lab page does.
- **The color picker** (`media/colorPicker.js`, `window.GBColorPicker`, also `module.exports` under Jest) is the Lab's only color control; add no `<input type="color">`. `GBColorPicker.create({ label, value, className, bounds, onInput, onChange, onCancel })` returns a trigger, a `secondary gb-cp-trigger` button (plus `className`) showing `value` as a swatch whose `data-color` holds the hex. Clicking it opens the picker right after it, `role="dialog"`, positioned `fixed` under the trigger so a scrolling dock does not clip it; one picker is open at a time. The picker keeps L, C and H as numbers and passes `GB.oklchToHex` of them on: `onInput(hex)` on every change, `onChange(hex)` once on Enter or a pointer press outside the picker and its trigger, and `onCancel()` once on Escape, which goes no further than the picker. Either way focus returns to the trigger. `bounds` `{ l: [min, max], c: [min, max] }` clamps L and C after every change. `trigger.setValue(hex)` changes the swatch and the color the picker opens on next. `GBColorPicker.blocks(hex, step)` returns the five lightness blocks `{ hex, l, disabled }` at lightness l0 - 2 step to l0 + 2 step, at the color's chroma and hue; a block past 0 or 1 is disabled. The head has a Smooth / Facets toggle (`.gb-cp-mode`, `aria-pressed`). Facets draws the ring as 24 flat 15 degree tiles and the panel as 11 lightness rows (0.1 apart) by 12 chroma columns (0.03 apart), and a press or an arrow key lands on a tile's value (`FACETS`); typed fields and the lightness blocks stay exact. The mode is module state, kept in `localStorage` under `gb.colorPicker.facets` where storage works, so every picker opens in the last mode chosen. The gamut note asks `GB.oklchInGamut({ l, c, h })`, the channel check `oklchToHex` makes before it lowers chroma. In `palette.js`, `colorPicker()` wraps `create` for the four places: it takes a snapshot when the picker opens, and on Escape puts the step 6 result line back and hands the snapshot to that place's `cancel`, which restores what it changed, saves and redraws. The CSP adds `font-src ${webview.cspSource}` for the codicon font, which the previews draw with.
- **Gallery rules** (`media/gallery.js`):
  - Paint mock widgets only through `paint()` / `P()` with a key spec such as `{ bg: 'button.background', fg: 'button.foreground' }`. That records the keys in `data-keys`, which feeds the chips, the definitions table, hover linking and contrast pairs. A color set any other way is invisible to all four.
  - `gallery.css` sizes and arranges mock widgets and never names a theme color for a mock part.
  - A key with no value in the current theme is recorded but not painted, because VS Code draws nothing for it either.
  - Adding a widget means adding one `CATALOG` entry. `test/gallery.test.ts` then checks it draws.
- **Restoring after reload**: each panel has a `WebviewPanelSerializer` and an activation event (`onWebviewPanel:gigglybits.themeLab`, `onWebviewPanel:gigglybits.themePreview`), which bring the Lab and its preview back after a reload, which helps when iterating under F5. Copirate does this in only two panels; here it is deliberate.

## Testing

- **Jest with ts-jest** for unit tests under `test/`, as in copirate. `jest.config.js` maps the `vscode` import to `test/__mocks__/vscode.ts`, a small stub driven by `mockState`. Extend the stub only with the API slice the code under test reads. A test that drives a panel host, which needs fake webview panels and commands the shared stub does not have, supplies its own `jest.mock('vscode', ...)` factory in its file instead, as `test/themePreviewPanel.test.ts` does.
- **Fixtures** live in `test/fixtures/`. `theme-ext/` is a fake theme extension with an `include` chain, a `package.nls.json` label and a null color, so the theme reader is tested against real files.
- **Test types are part of the build.** `package` runs `check-types:test`, so a type error in a test fails packaging, the same gate copirate added.

## Palette entries

The theme builder takes one palette entry. The build's base palette (`BASE` in `scripts/build-themes.js`) is one, without an `id` or `name`, and `test/fixtures/palettes.json` holds nine in a list, format version 1:

```json
{
  "version": 1,
  "palettes": []
}
```

The Palette Lab measures every candidate against three dark reference backgrounds, `#121212`, `#1e1e1e` and `#252526` (`SEED_BACKGROUNDS` in `media/palette.js`), and the live `editor.background` as a final column labelled "your editor". Each entry in `palettes` has these fields:

| Field | Meaning |
|---|---|
| `id` | Stable id. Generated: `<rule>-h<hue>-l<lightness, 2 decimals>-c<chroma, 3 decimals>`, e.g. `triad-h210-l0.75-c0.130`. Pasted: `pasted-` plus the hex values without `#`, joined by `-`. `themeFileName` names a theme file after it. |
| `name` | Display name; `themeLabel` gives `GigglyBits Dark (<name>)`. |
| `source` | `generated` or `pasted`. |
| `rule` | Harmony rule id. Generated palettes only. |
| `baseHue` | Base hue in degrees, 0-359. Generated palettes only. |
| `lightness` | OKLCH lightness, 0.30-0.95. Generated palettes only. |
| `chroma` | OKLCH chroma, 0-0.30. Generated palettes only. |
| `colors` | 1-10 lowercase `#rrggbb` strings. |

Harmony rules (`HARMONY_RULES` in `media/shared.js`), in OKLCH. H is the base hue, L the lightness, C the chroma, and alt(x) means hue x with lightness L+0.08 and chroma C*0.8. Hues wrap modulo 360, lightness is clamped to 0.30-0.95, and a color outside sRGB loses chroma in 0.005 steps until it fits, which keeps its lightness and hue.

| Rule | Five colors |
|---|---|
| analogous | H-60, H-30, H, H+30, H+60 |
| monochromatic | hue H; lightness L-0.12, L-0.06, L, L+0.06, L+0.12; chroma C*0.6, C*0.8, C, C*0.8, C*0.6 |
| triad | H, H+120, H+240, alt(H), alt(H+120) |
| complementary | H, alt(H), H+180, alt(H+180), H with chroma C*0.5 |
| split-complementary | H, H+150, H+210, alt(H), alt(H+150) |
| square | H, H+90, H+180, H+270, alt(H) |
| compound | H, H+30, H+165, H+195, alt(H) |
| shades | hue H, chroma C; lightness L-0.16, L-0.08, L, L+0.08, L+0.16 |

Preview mapping, one panel per background: color 1 colors keywords, color 2 function names, color 3 strings, color 4 type names and color 5 numbers; plain text uses the live `editor.foreground` and comments the live `descriptionForeground`. Color 1 also fills the button (with black or white text, whichever contrasts more), is the focus ring, and at 30% opacity is the selection; color 2 fills the badge. A pasted palette with fewer than five colors repeats its colors from the start.

## Building the theme itself

The extension ships 13 themes: **GigglyBits Dark (Lab)** and the slots **GigglyBits Theme 1** to **12**. They are generated, never edited by hand, all from the base palette `BASE` in `scripts/build-themes.js` (the triad at hue 210, lightness 0.75 and chroma 0.13 that the Lab's defaults also start from), so each looks finished before scoped settings color it:

- `npm run themes` (`scripts/build-themes.js`) writes `themes/gigglybits-lab-color-theme.json` and the 12 slot files, deletes any `themes/gigglybits-dark-*-color-theme.json` an older build wrote, and rewrites `contributes.themes` in `package.json` to the Lab entry, then the 12 slots in order. Commit the result, so F5 and a reader of the repository see the real themes.
- `npm run themes:check` writes nothing. It exits 1 with `Themes out of date:` and the files that would change, or prints `Themes up to date: Lab theme and 12 slots`. `package` runs it, so a change to `BASE` or the builder made after the last `npm run themes` stops the build until you run `npm run themes` again.
- `media/themeBuilder.js` turns one palette into a theme, and `scripts/theme-builder.js` re-exports it for the build and the extension host. The Theme Lab loads the same file, so its previews draw exactly what Try in VS Code applies. It uses the color math in `media/shared.js`, and `test/themeBuilder.test.ts` pins its rules.
- The Lab theme is the target of the Palette Lab's **Try in VS Code** button (below).

**Try in VS Code** applies the current Lab candidate without a reload. The extension host bundles `scripts/theme-builder.js` (typed by `scripts/theme-builder.d.ts`) and calls `labSettings(entry, chrome, edits)`, the chrome carrying the syntax set's colors as `syntaxColors` when the design is on a set (Syntax sets, below), so the applied colors are the builder's, not a second implementation. `src/labSettings.ts` holds the settings edits:

- The theme colors and token rules go into user settings under `"[GigglyBits Dark (Lab)]"` in `workbench.colorCustomizations` and `editor.tokenColorCustomizations`, and `workbench.colorTheme` switches to the Lab theme. Theme-scoped blocks apply only while that theme is active, so other themes are untouched. The confirmation offers to switch back to the previous theme.
- Try in VS Code writes its colors only to user settings, and removes a `[GigglyBits Dark (Lab)]` block from the workspace value and, in a multi-root workspace, from each folder value of `workbench.colorCustomizations` and `editor.tokenColorCustomizations` (`withoutLabScope` in `src/labSettings.ts`, `removeShadowingLabColors` in `src/themeLabPanel.ts`), because a copy at either level outranks the user block key by key and hides the Try; the status bar names the file cleaned. Something outside this extension wrote such a copy into `d:/VSCodeWorkspaces/gigglybits-vscode-theme.code-workspace` twice (2026-11-04 and 2026-11-06); the writer is not known. It switches `workbench.colorTheme` in the workspace whenever a folder is open, or when a workspace with no folders has a theme of its own, so a Try changes only this project; otherwise in user settings (`tryThemeTarget` in `src/themeLabPanel.ts`). A folder-level value keeps the user level, as before project-level Try. The message names the scope: "in this project only" or "in every window that doesn't set its own theme". Back restores the theme at the same level, and in a project that had no theme of its own it reads "Back to your default" and removes the workspace value. Saving a theme this folder uses needs nothing extra: `ThemeLibraryController.refreshProjectFrame` rewrites the folder's frame block whenever `gigglybits.library` changes. The Lab's previews draw the theme alone, never a folder's old color; with one present the Frame row says so. `gigglybits.openThemeLab` takes an optional `{ frame, name }` (`parseFrameSeed` in `src/themeLabPanel.ts`); the panel posts `frameSeed { frame, name }` after the ready sequence's `start`, or at once when the Lab is already open, and the page applies it through `seedFrame` in `media/palette.js`.
- The confirmation also says when something else wins: on a user-level Try, a folder-level `workbench.colorTheme` when `inspect` reports one; on any Try, `window.autoDetectColorScheme` (`themeOverrideNotes` in `src/themeLabPanel.ts`).
- The builder's `chrome` option picks the editor accent (`index`) and surface tint (`surfaces`), and its `frame` (`{ index | color, style }`) the Frame: the keys in `FRAME_KEYS`, which no editor setting decides in a Filled frame. With no `frame` the Frame is Dark and follows the accent, which reproduces the themes built before the Frame existed apart from the brighter input outlines and a transparent `window.activeBorder`; `test/fixtures/frame-baseline/` holds those themes, one per entry of `test/fixtures/palettes.json`, and `test/shared.test.ts` checks that `chromeColors()` agrees with the builder's default build on every surface style and accent.
- The Roles step adds three optional `chrome` fields, cleaned by `cleanChrome` in `media/themeBuilder.js`: `syntax`, five palette indexes for Keywords, Functions, Strings, Types and Numbers, read modulo the palette's length (absent or invalid, `[0, 1, 2, 3, 4]`); `depth`, a multiplier on every surface's lightness offset from the editor background, clamped to 0.5 to 2 and rounded to 0.1 (default 1); and `text`, a `TEXT_LEVELS` id, `soft`, `standard` (default) or `high`, setting the four gray text lightnesses. With all three at their defaults the build is the one before they existed, which `test/themeLibrary.test.ts` checks against `test/fixtures/design-baseline-settings.json`. `ROLE_FAMILIES` lists the seven families the Roles step shows, Syntax, Accent, Surfaces, Text, Status, Terminal and Frame, each `{ id, name, how, roles }`, and every swatch belongs to exactly one. The Lab's `designOf`, its Try `settings` and its `themeOf` chrome carry each field only when it differs from its default (`roleSettingsOf` in `media/palette.js`), so a design made without touching them saves and tries exactly as before; `parseTryRecord` and `parseDesign` keep valid fields and drop invalid ones.

How a palette becomes a theme:

- **Background**: every theme draws the editor on `#1e1e1e`. Light and high-contrast themes are not built yet.
- **Syntax roles**, in the Palette Lab's preview order: color 1 colors keywords, color 2 functions, color 3 strings, color 4 types and color 5 numbers. A palette with fewer than five colors repeats from the start. Comments are a muted neutral in italic, and plain text keeps the editor foreground.
- **Readability lift**: a role color below 4.5:1 on `#1e1e1e` has its OKLCH lightness raised in 0.01 steps, keeping hue and chroma, until it reads at 4.5:1.
- **Separation**: then, in role order, a role closer than 0.05 in OKLab to an earlier role is raised in 0.02 steps until it is at least 0.05 from all of them. Roles that come from the same palette color (a short palette repeating) are left equal. Lightness never goes past 0.95. The Log Cabin palette in `test/fixtures/palettes.json` needs this: lifting lands both of its blues on `#378bd3`.
- **Surfaces**: a neutral ramp stepped from the background in OKLCH, at chroma 0.01 in color 1's hue: deep (-0.025) for the side bar, activity bar, panel, status bar, title bar and inactive tabs; line (+0.025) for the current line and tab hover; raised (+0.045) for widgets, menus, inputs and dropdowns; hover (+0.07); borders (+0.11). Text sits at lightness 0.87, muted text at 0.68 and faint text at 0.50.
- **Accent**: color 1, after lifting, for buttons, the focus border, badges, the progress bar, active borders and links. Button text is black or white, whichever contrasts more. Selections and highlights are color 1 at reduced alpha (30% for the selection), as in the Palette Lab preview; find matches use color 2.
- **Status colors** keep fixed hues (error 25, warning 85, success 145, info is color 1) at color 1's lightness and chroma (chroma at least 0.1, so a gray palette still gets a red that reads as red), lifted to 4.5:1 like the roles. Terminal ANSI colors use fixed hues too, so program output keeps its meaning.
- **No `include`**: every theme stands alone and inherits nothing from a built-in theme.

What the theme deliberately leaves alone, because specialized extensions own it:

- **Syntax is a baseline only.** The token rules use only these language-neutral root scopes (`GENERIC_SCOPES`): `keyword`, `storage.type`, `storage.modifier`, `entity.name.function`, `support.function`, `string`, `entity.name.type`, `entity.name.class`, `support.type`, `support.class`, `constant.numeric`, `constant.language`, `comment`. There are no `semanticTokenColors`. Token color settings and decorations from an extension or from your settings apply over a theme, so a theme with only broad rules gives every language a readable default and adds no opinion an extension has to fight. `semanticHighlighting` is `true` so semantic tokens from language extensions still show; without it they are off under the default `editor.semanticHighlighting.enabled` value.
- **Workbench colors are exactly the keys the element gallery draws** (510 on 2026-11-06), apart from `UNSET_KEYS`. The gallery keys are gathered over one render per activity bar position, so the `activityBarTop.*` keys drawn only at the top or bottom count. No other key is set, so a theme never sets a color key a third-party extension registers. `test/themeBuilder.test.ts` renders the gallery and fails when its key set and the theme's differ, so a widget added to the gallery needs its key placed in `KEY_GROUPS` (or in `UNSET_KEYS`) before the tests pass.
- **`UNSET_KEYS`**, the gallery keys left unset on purpose (at most 10):

| Key | Why it stays unset |
|---|---|
| `contrastBorder` | A high-contrast border. In a dark theme it draws an extra border around nearly every part of the workbench. |
| `contrastActiveBorder` | The same for the active element: an extra border around every focused or active part. |
| `editor.selectionForeground` | Recolors selected text, replacing its syntax colors, an extension's included. VS Code leaves it unset outside high contrast. |
| `editor.findMatchForeground` | Recolors the text of the current find match, replacing its syntax colors. |
| `editor.findMatchHighlightForeground` | Recolors the text of the other find matches, replacing their syntax colors. |
| `terminal.selectionForeground` | Recolors selected terminal text, replacing the colors the program printed. |

### Coverage: a decision for every VS Code color

Every color VS Code and its built-in extensions register has exactly one decision:

- **Set and drawn**: in `KEY_GROUPS` under an existing swatch, and painted in a gallery card. The rule for what gets set is the main chrome and what you look at every day.
- **Drawn but unset**: in `UNSET_KEYS`, above.
- **Left to VS Code**: in `LEFT_TO_VSCODE` in `media/themeBuilder.js`, a list of `{ area, reason, keys, prefixes, except }` groups. A prefix such as `chat` covers every id starting `chat.`, not `chatX`, apart from the ids in `except`, which the theme sets anyway.

`test/fixtures/vscode-colors.json` is the snapshot of what VS Code registers: `{ vscodeVersion, generatedAt, sources, ids }`. `scripts/vscode-colors.js` builds it from the workbench bundle (`out/vs/workbench/workbench.desktop.main.js`), taking every call of the minified color registry function, found by the name of the function that registers `editor.background`, plus the ANSI colors the terminal registers in a loop. It reads the Agents window's bundle (`out/vs/sessions/sessions.desktop.main.js`) the same way, since that window registers a few colors the workbench does not. It also reads `contributes.colors` from every built-in extension's `package.json`. `test/themeCoverage.test.ts` checks each snapshot id against the three decisions and names every id that has none or more than one.

After a VS Code update:

1. Run `npm run colors:snapshot`. With no argument it takes the highest version under `%LOCALAPPDATA%/Programs/Microsoft VS Code`; pass the path to `workbench.desktop.main.js` to read another install.
2. Run `npx jest test/themeCoverage.test.ts`. It names each new color that has no decision.
3. For each one, either set it (a `KEY_GROUPS` entry, a gallery drawing, then `npm run themes`) or add it to a `LEFT_TO_VSCODE` group with a reason. Commit the refreshed snapshot with the decisions.

`test/themeBuilder.test.ts` also holds the everyday list and the chat and terminal prefixes as data. Its `{#everyday-set}` and `{#areas-set}` tests fail when one of those colors is neither set and drawn nor left to VS Code.

Checking a theme:

- Put `"$schema": "vscode://schemas/color-theme"` at the top of a theme file (the generated ones have it) to get completion and validation for color keys.
- Use step 2's contrast table and the preview window's contrast line as the readability check. 4.5:1 is the WCAG AA minimum for body text.
- Built-in commands worth knowing:
  - **Developer: Inspect Editor Tokens and Scopes** shows which TextMate scope and semantic token style applies under the cursor.
  - **Developer: Generate Color Theme From Current Settings** writes VS Code's own snapshot of the current colors, a useful comparison against a theme file `npm run themes` writes.
- F5 is the fastest loop for theme JSON too: edit the file, then reload the dev host window.

## Theme library

Saved themes live in the user setting `gigglybits.library` (scope `application`, so a workspace cannot override it and Settings Sync carries it). Each entry is a `SavedTheme`: `id`, `name`, `slot` (1 to 12 or null), `design` (the Lab's whole state: mode and rule settings or pasted colors, `colors`, `chromeIndex`, `surfaces`, `frame`, `edits`; see Edits as shifts, below) and `savedAt`. A `groups` field written while style groups existed is ignored when read. `design.syntaxSet`, when present, is the id of the syntax set the theme's code colors come from (Syntax sets, below).

- `src/themeLibrary.ts` holds every decision, with no `vscode` import: `parseLibrary` (drops invalid entries, reusing `parseTryRecord` for the design), `saveTheme` (same name updates, a new name takes the lowest free slot, `needsSlot` when all 12 are bound), `bindTheme`, `deleteTheme`, `slotSettings` (the same `labSettings` Try in VS Code uses), `writeSlot` / `clearSlot`, which edit the `[GigglyBits Theme <n>]` blocks of the user `workbench.colorCustomizations` and `editor.tokenColorCustomizations`, and the syntax set functions `parseSyntaxSets`, `saveSyntaxSet`, `setDefaultSyntaxSet`, `deleteSyntaxSet`, `themesUsingSyntaxSet`, `syntaxColorsFor` and `writeAllSlots` (Syntax sets, below).
- `src/themeLibraryController.ts` is the VS Code side: settings writes, the delete modal, the slot quick pick, Use in this project (`workbench.colorTheme` at the Workspace target; it writes `projectColors`, which removes an old folder color, and when one was found clears whichever of the undeclared `gigglybits.identity.hue` and `pinnedColor` is set, ignoring a refused write, and says so in the status bar), Use everywhere (Global target) and the `gigglybits.chooseTheme` command.
- **The frame belongs to the project.** The user `[GigglyBits Theme <n>]` blocks come from `everywhereSettings`: the theme with a Dark frame and its frame edits left out. Use in this project also writes `projectFrame` (the `FRAME_KEYS` of the full theme, 31 keys: the bars, the window border and, since 2026-11-05, the six tab and split lines `tab.activeBorderTop`, `tab.activeBorder`, `editorGroup.border`, `sideBar.border`, `panel.border` and `sash.hoverBorder`, which a Filled frame draws in its color lifted to 3:1) into the folder's `workbench.colorCustomizations` under `[GigglyBits Theme <n>]`, removing any other slot's block; a workspace theme-scoped block beats the user block key by key (Identity write shape, below). Each window runs `projectFrameRefresh` at activation and whenever `gigglybits.library` changes, so a re-saved frame reaches open projects and a deleted theme's projects lose the block.
- **Saves build on the settings files, not the window's configuration.** A window that was already open held an older library in its configuration and its save wrote back an older theme (live check, 2026-11-04). Before every library or slot write the controller reads the values from disk: `settingsFilesFor(context.globalStorageUri)` names the default profile's `User/settings.json` for the application-scoped library and the window profile's `settings.json` for the color settings, and `freshestSetting` parses them with `jsonc-parser`, falling back to the configuration when a file is missing or does not parse. A disagreement is logged to the **GigglyBits** output channel.
- The slots are 12 theme files, `themes/gigglybits-theme-<n>-color-theme.json`, labelled `GigglyBits Theme <n>`. `npm run themes` writes them after the Lab theme, built like it from the base palette. `SLOT_COUNT`, `slotLabel` and `slotFile` live in `media/themeBuilder.js`.
- Webview messages: the page posts `saveTheme { name, design }`, `useTheme { id, where: 'project' | 'everywhere' }`, `deleteTheme { id }`, `saveSyntaxSet { id?, name, colors }`, `setDefaultSyntaxSet { id | null }` and `deleteSyntaxSet { id }`, and its `applyPalette` chrome carries `syntaxColors` when the design is on a set; the host sends `library { themes, syntaxSets, hasFolder }` on `ready` and whenever `gigglybits.library` or `gigglybits.syntaxSets` changes, `installedStarters { starters }` last on `ready` and whenever extensions change (Start set from, below), and `start` may carry `saved { name, design }` when the active theme is a bound slot.

### Accent groups

`ACCENT_GROUPS` in `media/themeBuilder.js` names six sets of keys the accent colors (Buttons, Badges and progress, Links, Selection and highlights, Focus outlines, Cursor); every key is in an Accent-family swatch and outside `FRAME_KEYS`, which `test/themeBuilder.test.ts` checks. `chrome.accentGroups` is `{ [id]: { index } | { color } }`, cleaned by `cleanAccentGroups` and returned by `cleanChrome`; `color` is a shift from the base like a custom frame color. `buildColors` runs `applyAccentGroups` after `KEY_GROUPS` and before key edits: each group's keys take their swatch from `accentSet(color)`, the Accent family the builder's accent rules make from that one color (it equals `swatches()` for the accent color itself). While `edits.swatches.accent` is set, groups are skipped; an edit to another Accent-family swatch keeps that swatch for its keys. The setting rides with the Roles settings: the Lab's `roleSettingsOf` includes it, so Try, Save and Load carry it, and `parseRoleSettings` (`src/labStart.ts`) and `roleChrome` (`src/themeLibrary.ts`) pass it to the host's builds.

### Custom accent and step 3's example chips

`chrome.color` is a custom editor accent, a shift from the base (or a fixed `#rrggbb`) used in place of `chrome.index`. `accentSource(entry, chrome)` in `media/themeBuilder.js` resolves it; `swatches()` lifts it and tints the surfaces from it exactly as it would a palette pick, and `frameOf` falls back to it for a frame with no color or index. The Lab keeps it as `accentColor` in its state, the saved design (`Design.accentColor`) and the Try record (`TryRecord.accentColor`, checked by `parseTryRecord`); `roleChrome` in `src/themeLibrary.ts` passes it to slot builds, and `everywhereSettings` gives the Dark frame that color. Step 3's Frame style and Surfaces chips draw `miniWindow(sw)` in `media/palette.js`, a small window from the swatches `swatches()` returns for that choice, so each chip shows the colors it would build.

### Edits as shifts

An edit and a custom frame color are stored as a shift, the string `~dl,dc,dh` (OKLCH lightness, chroma and hue offsets) with an optional `/aa` alpha byte, so they follow the palette when the base color or rule changes. `media/themeBuilder.js` owns the format: `shiftFor(target, from)` measures one, `applyShift(shift, from)` applies it, and `cleanEdits` accepts shifts, fixed `#rrggbb` / `#rrggbbaa` colors and `default` for a key.

- A role edit is measured from the swatch the builder works out without that edit (`preferredSwatch`); a key edit from the key's value after roles and accent groups (`preferredKey`). A shift edit of a role in `LIFTED` (the syntax roles, the accent, the status colors and the input border) is lifted to its contrast on `THEME_BACKGROUND` after the shift. A single-key edit is not lifted, because a key's role does not say whether that key draws text.
- A custom frame color is measured from the entry's `base` (`baseColor(design)`: the Wheel's base color, or a pasted palette's first color; color 1 when `base` is missing). The Lab passes `base` in Try's entry, and `slotSettings` and `everywhereSettings` pass it for saved themes.
- A fixed color still builds exactly as before, so an older saved theme looks the same when used. The Lab converts fixed colors to shifts when it reads its state (`shiftFixedColors` in `media/palette.js`, through `toShifts`), and every edit it makes goes through `toShifts` too. A key the theme leaves unset has nothing to measure from and keeps its fixed color.

### Syntax sets

Syntax sets replaced style groups on 2026-11-07. A style group mapped a widget family's colors to theme roles, and those roles come from each theme's palette, so groups could not keep code colors the same across themes. The user setting `gigglybits.groups` is no longer declared (since 0.1.1, the first Marketplace release) and nothing reads it.

Syntax sets live in the user setting `gigglybits.syntaxSets` (scope `application`, read from and written to the same default-profile `User/settings.json` as the library, at the Global target). Each entry is a `SyntaxSet`: `id`, `name`, `colors` (one `#rrggbb` for each of `SYNTAX_SET_KEYS`: keyword, function, string, type, number, comment, tag, attribute, variable, property, constant, operator, regex), `isDefault` and `savedAt`.

- The builder never sees a set's id. Callers resolve `design.syntaxSet` (or the Lab state's `syntaxSet`) to colors and pass them as `chrome.syntaxColors`; `cleanChrome` returns them only when every key is a `#rrggbb`, otherwise null, and a design naming a set that no longer exists builds as From this palette.
- With `syntaxColors`, `swatches` takes the five code roles (`kw` to `num`) from the set instead of `roleColors`, each lifted to 4.5:1 on `THEME_BACKGROUND` with its hue and chroma kept and no keep-apart pass, and role edits still apply on top. `tokenColors` returns today's six rules in the set's colors (Comment from `comment`, Number without `constant.language`) followed by `SET_RULES`: Tag, Attribute, Variable, Property, Constant, Operator, Regex and Keyword operator, each with its scopes. Without `syntaxColors` the output is exactly as before, so palette themes and the committed theme files do not change.
- `parseSyntaxSets` drops a set missing a color or a name and keeps only the first set marked default. `saveSyntaxSet` updates the set with the given id or adds one that is not the default. `deleteSyntaxSet` also removes `syntaxSet` from every saved theme that named the set and returns how many. `slotSettings`, `everywhereSettings`, `writeSlot` and `writeAllSlots` take the sets and build each theme with its set's colors.
- The controller writes `gigglybits.syntaxSets` and then rewrites every bound slot through `writeAllSlots`, after a save, a default change or a delete. A delete of a set some saved theme uses asks first in a modal naming the number of themes. Like the library's own writes, a set change rewrites slot blocks only in the profile of the window that made it.
- In the Lab, step 4's Syntax family shows a source choice: From this palette (the Colors row) or each set by name. On a set it shows the set's thirteen colors as pickers, how many saved themes use it, a Name field, Make default and Delete set; a kept color posts `saveSyntaxSet` for that set. Save New Set posts the code colors as drawn: from the palette build, or the current set's own colors when on a set. `roleSettingsOf` carries `syntaxSet`, so Save theme's design, Try's record and the loads (`takeRoleSettings`) keep it. The default palette start (`themeLab.js` `applyStart` with no Try record and no saved theme) takes the default set.

#### Start set from: syntax set starters

The Syntax family's **Start set from** row, under Code colors (`startRow` in `media/palette.js`), fills an unsaved draft from one of three sources. It shows one group at a time (`starterGroups`: Installed themes, Well-known schemes, From your palette, as `gb-ke-seg` buttons with `data-group` and their counts) and the group's starters as chips (`gb-ss-chip`, `data-key` the starter's key), each drawing three lines of code (`chipCode`) in the starter's colors through `setColor` on the editor background, with a second line of credit, recipe description or lightened count. A group shows `CHIPS_SHOWN` (8) chips until Show all. The group shown and Show all live in `syntaxDraft` beside the draft, never in `ctx.ui`; with no installed dark themes the Lab opens on Well-known schemes and the Installed group says "No dark themes installed". The builder side is in `media/themeBuilder.js`; the host side in `src/themeSource.ts`.

- `SYNTAX_SCHEMES` holds the bundled well-known schemes as `{ id, name, author, license, url, colors }`: `dracula`, `nord`, `solarized-dark`, `gruvbox-dark`, `one-dark`, `tokyo-night` and `catppuccin-mocha`. `author`, `license` and `url` name each scheme's original repository; README.md's Credits section repeats them. A kind takes the scheme's own published syntax guidance where it names one (the Dracula spec, the Nord docs, the Tokyo Night README palette, the Catppuccin style guide), else its Base16 port in tinted-theming/schemes (MIT) through this slot map: base0E keyword, base0D function, base0B string, base0A type, base09 number, constant and attribute, base08 variable and tag, base0C regex, base03 comment, base05 operator and property. Solarized Dark, Gruvbox and One Dark come entirely from their ports. Keep a scheme only when its license is permissive; Gruvbox states MIT/X11 in its README and has no LICENSE file.
- `starterFromRules(rules, foreground)` reads a theme's token rules (`{ scope, foreground? }` in theme order, the shape `TokenRule` already has, `'(editor default)'` for a rule with no scope) into the thirteen colors. Each kind probes one scope (`STARTER_PROBES`): keyword `keyword`, function `entity.name.function`, string `string`, type `entity.name.type`, number `constant.numeric`, comment `comment`, tag `entity.name.tag`, attribute `entity.other.attribute-name`, variable `variable`, property `variable.other.property`, constant `variable.other.constant`, operator `keyword.operator`, regex `string.regexp`. A selector matches when it equals the probe or is a dot-segment prefix of it, a selector with a space (a descendant selector) is ignored, the match with the most segments wins and a tie goes to the later rule. A kind with no match takes the last `(editor default)` foreground, else `foreground`, else `#d4d4d4`. Colors come out as lower-case `#rrggbb` (`#rgb` expanded, alpha dropped); a rule with no hex foreground counts as no match. So `keyword.control` never wins the keyword probe: Dark+ gives `if` and `return` its `keyword` blue.
- `recipeColors(id, { sw, foreground, comment, baseHue })`: `quiet` keeps the drawn `sw.str` (string, regex), `sw.num` (number, constant) and `sw.fn` (function, type), draws comments in `comment` and everything else in `foreground`. `harmony` draws OKLCH lightness 0.78, chroma 0.12 at keyword H, attribute H+30, function H+60, string H+120, type H+180, number and constant H+240, tag H+300, regex at lightness 0.70 and H+120, comment at lightness 0.66, chroma 0.03 and H, and variable, property and operator in `foreground`. `harmonyHue(frameHex, accentHex)` is the frame's hue when its chroma is at least 0.03, else the accent's; the Lab passes `theme.sw.frameBg` and `theme.sw.accent`.
- `setColor` (the 4.5:1 lift every set color gets) and `cleanSyntaxColors` are exported, so the Lab can name the kinds a draft's colors will be lightened for and check an installed starter's colors.
- `listInstalledSyntaxStarters()` in `src/themeSource.ts` returns `{ id, label, extension, colors }` for every `vs-dark` theme contribution of every extension except this one (`ownExtensionId()`: `<publisher>.<name>` read from this extension's own package.json, one folder up from both `dist/` and `src/`, compared in lower case, so a rename follows). It loads each theme file with its include chain through `loadThemeFile` into a fresh snapshot and maps its token rules with `starterFromRules`, passing the theme's `editor.foreground`; a theme with no token rules (including a `.tmTheme` reference) is left out, and semantic token colors are not read. `ThemeLabPanel` posts `installedStarters { starters }` last in the `ready` sequence, after `identity`, and again on `vscode.extensions.onDidChange`; a failure to read them posts an empty list.
- In the page, `themeLab.js` keeps the latest `installedStarters` list (never saved) and passes it as `ctx.installedStarters`. A pick builds the draft `{ key, name, source, colors }` in the module-level `syntaxDraft`, outside `ctx.ui`, so a redraw keeps it and a reload, a render with another ui state, a Code colors change, Discard draft or Save New Set drops it. While it exists the Syntax family shows its line, Discard draft, a line naming each kind (in `SET_LABELS` words) whose color `setColor` changes, and thirteen pickers that edit the draft only, and the code sample draws `tokenColors` and `swatches` with `chrome.syntaxColors` set to the draft, so the design's role edits apply on top as they would on a set. Nothing about a draft is saved or posted until Save New Set, which posts `saveSyntaxSet { name, colors }` with the draft's current colors and the starter's name prefilled, and leaves Code colors where it was.

The retired per-folder color wrote a `[GigglyBits*]` block, which matches the slot labels too, so an old folder color covers a saved theme's frame. That is why Use in this project removes it.

## First run and theme scope

- **Get Started walkthrough.** `package.json` contributes one walkthrough, `getStarted`, with three steps whose pages are `media/walkthrough/open-lab.md`, `try.md` and `default.md`. The first step's description ends with a `command:gigglybits.openThemeLab` link and completes on that command. VS Code opens a walkthrough by itself only for an extension installed while the window is running, in a focused window, the first time that profile sees it, with `workbench.welcomePage.walkthroughs.openOnInstall` on (read in the installed build's `workbench.desktop.main.js`, 2026-11-08). An extension installed before VS Code starts, as the UI driver's `--vsix` does, does not count, so checking the auto-open needs Extensions: Install from VSIX... in a running window on a fresh profile.
- **Theme-scope line.** On ready, after `start`, and on every configuration change affecting `workbench.colorTheme`, `ThemeLabPanel` posts `themeScope { window: { label, source }, defaultTheme }` from `themeScopeOf` in `src/themeLabPanel.ts`: a folder or workspace value is source `project`, else the user value is `default`, else `vscode` with a null label. `themeScopeLine` in `media/palette.js` draws step 1's sentence from it, and its **Change default** button posts `changeDefaultTheme`. The host answers with a quick pick of `listInstalledThemes()` (`src/themeSource.ts`: every contributed theme, light and GigglyBits' own included, id `theme.id ?? label`), the current user value described `current default`, and writes the pick to the user-level `workbench.colorTheme`.
- **Leftover colors.** After `themeScope`, and on every change to `workbench.colorCustomizations` or `editor.tokenColorCustomizations`, the panel posts `leftovers { colors, tokens }`: the user-level keys outside every `[...]` theme block (`unscopedKeys` in `src/labSettings.ts`, skipping the token setting's `semanticHighlighting` switch, `TOKEN_KEYS_KEPT`). Workspace values are never read, since a color extension such as Peacock writes them on purpose per project. `leftoversNote` in `media/palette.js` names the first five and counts the rest, and **Remove them** posts `removeLeftovers`, which `ThemeLibraryController.removeLeftoversSafely` handles: it builds on `slotValues()` (the settings file, as slot writes do), asks in a modal, reads again after the modal, and writes `leftoverRemoval`'s kept values through `writeSlotValues`.
- **Step 1's complete-theme line.** Step 1 ends with a line saying it makes a complete theme, and the headings of steps 2 to 5 carry an Optional tag (`.gb-step-opt`), which `syncSteps` carries into each heading's collapse button.

## Identity write shape

History: nothing writes this overlay since the per-folder color was retired into project frames (2026-11-05). The shape stays recorded because `oldFolderColor` and `withoutIdentity` find and remove it in folders that still have it.

Settled live on 2026-11-03 against the installed 0.0.6. The question: which workspace `workbench.colorCustomizations` shape shows a workspace identity under a GigglyBits theme whose design lives in a user-level theme-scoped block, without erasing that design.

How it was measured: user settings held the Lab design under `[GigglyBits Dark (Lab)]` (`statusBar.background` `#131a1b`, `button.background` `#20c3d9`). Each shape replaced the workspace's color block in turn, and a Developer Tools console poller read `--vscode-statusBar-background` and `--vscode-button-background` from `.monaco-workbench` (that selector returned values, so `document.body` was not needed) every time either changed. Each shape used its own red, so every reading identifies the shape that produced it.

| Workspace shape | Theme | `--vscode-statusBar-background` | `--vscode-button-background` | Passes |
|---|---|---|---|---|
| A: unscoped plus `[GigglyBits*]` (`#ff0001`) | GigglyBits Dark (Lab) | `#ff0001` | `#20c3d9` (the user Lab block's value) | yes |
| B: unscoped plus each exact GigglyBits label (`#ff0002`) | GigglyBits Dark (Lab) | `#ff0002` | `#20c3d9` | yes |
| Unscoped only (`#ff0003`) | GigglyBits Dark (Lab) | `#131a1b` (the user Lab block wins) | `#20c3d9` | no |
| Unscoped only | GigglyBits Dark (Candy) | `#ff0003` | `#20c3d9` (Candy's own) | shows, no user block for Candy |
| Unscoped only | Dark Modern | `#ff0003` | `#0078d4` (Dark Modern's own) | shows |

**Chosen shape: A.** Write the overlay unscoped, so it shows under any theme, and again under `[GigglyBits*]`, so it beats the user-level theme-scoped design block without touching that block's other keys. The wildcard also matches theme labels added later, such as the design library's slots, so nothing needs to list them.

What the measurements also show:

- **An unscoped workspace key loses to a user-level theme-scoped key.** VS Code merges the levels first and then lets theme-scoped blocks override unscoped keys, so the scope wins over the level. That is why the identity is written twice.
- **A workspace theme-scoped block beats the user block for the same theme**, key by key. Before the test, the everyday window's workspace held an older full Lab design under `[GigglyBits Dark (Lab)]`, and its `button.background` (`#ba7922`) showed instead of the user block's `#20c3d9`. Any design keys left at workspace scope therefore override the user's Lab design.
- **"Workspace settings" means the `.code-workspace` file when the window was opened from one.** VS Code then ignores window-level settings such as `workbench.colorCustomizations` and `workbench.colorTheme` in a folder's `.vscode/settings.json`: a first run that edited only that file changed nothing. `ConfigurationTarget.Workspace` writes to the right file in both cases; that is VS Code's documented behavior, and the 0.0.7 live checks ran only in single-folder windows, so an identity write into a `.code-workspace` file has not been observed yet.
- **The extension does not run in Restricted Mode.** `package.json` declares no `capabilities.untrustedWorkspaces`, so VS Code disables it in an untrusted folder: no offer, no commands. Live checks need their scratch folders trusted (a folder under `%TEMP%` is not, by default).
- **Identity cannot tell its keys from anyone else's.** The retired Set, Next and Clear commands stripped every identity key, and Remove the color and Use in this project still strip every identity key (`IDENTITY_KEYS`) at the top level, under `"[GigglyBits*]"` and under `"[GigglyBits Dark (Lab)]"`, whoever set it, so in a Peacock folder they replace or remove Peacock's colors. Finding an old color no longer reads the top level: `drawnOldColor` reads only the `"[GigglyBits*]"` block, which only the old overlay wrote and which VS Code draws over every GigglyBits frame, and `oldFolderColor` adds a pinned color. So a Peacock folder is no longer offered a project theme in Peacock's color, and the Frame row's note no longer calls Peacock's color GigglyBits' old one.
- **Start-up repair (0.0.11).** `refresh()` rewrites a pinned color only when the regions setting changes, so a workspace whose `"[GigglyBits*]"` copy went missing kept an unscoped-only overlay, which loses to the user-level Lab block as measured above. Once at activation, `IdentityController.register()` checks `overlayIncomplete()` from `src/identity.ts`: with a folder open and an identity set, any key of the current regions' overlay missing from the top level or from a `"[GigglyBits*]"` block, or the block itself missing, rewrites the overlay with the identity's fill. It checks key presence only, never values, so a complete overlay whose border shade came from another theme's background is not rewritten on every start.

## Packaging details

- **Publisher** is `EdgeInformation` and the name `gigglybits-theme-lab` in the working tree's package.json (edited 2026-11-07 for marketplace publishing), so the next build's extension ID is `edgeinformation.gigglybits-theme-lab`; `listInstalledSyntaxStarters` reads it from package.json (`ownExtensionId`). Builds 0.0.8 to 0.0.32 were `Websolete`, ID `websolete.gigglybits-vscode-theme`, and releases up to 0.0.7 were `EdgeInformation` with the old name, as in every sibling; VS Code treats each of these IDs as a different extension, so uninstall the build with the old ID before installing one with a new ID. Settings are keyed by their own names and carry over. `context.workspaceState` does not: VS Code stores it under a row named after the extension ID, so the identity offer's `gigglybits.identity.declined` flag (written by Not here and by Clear Workspace Color, read in `src/identityController.ts`) starts empty under the new ID, and a declined folder is offered a color again whenever `shouldOffer()` in `src/identity.ts` would offer one to a folder that never declined.
- **`engines.vscode`** is `^1.90.0`. There is no family-wide policy: the siblings range from `^1.85.0` to `^1.101.0`. Raise it only when an API you use needs a newer release.
- **`.vscodeignore`** is a deny list. vsce keeps a file if any `!` negation line matches it, whatever the order (noted in copirate's `.vscodeignore`), so keep negations rare and narrow. Check what shipped with `npx vsce ls`.
- `pack` runs `vsce package --no-dependencies`: the bundle in `dist/` carries everything at run time. The repository field and `LICENSE` are in place, so vsce no longer stops to ask about either; if one goes missing it asks again, which hangs a task.

## Windows and tooling gotchas

These come from copirate's recorded experience on this machine.

- **Do not `sed -i` a repo file on Windows.** It strips carriage returns, and `git diff` hides the change.
- **Line-ending checks can mislead.** When it matters, count bytes rather than trusting a tool's CRLF report.
- **Never run `npm audit fix --force`.** It makes breaking major-version jumps across the dependency tree.
- **PowerShell 5.1 has no `&&`.** Chain commands inside npm scripts, which run under `cmd.exe`, rather than in task `command` strings.
- **A blank webview that survives a window reload** usually means a wedged renderer. Close the tab and reopen it; restarting VS Code is the fallback.
- npm 11 holds back install scripts for `@vscode/vsce-sign` and `keytar`. Packaging works without them. They matter only for `vsce publish`, which this repo does not use.
